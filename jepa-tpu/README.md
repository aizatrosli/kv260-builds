# TPU-KV260 simulation + a hard-coded tiny JEPA encoder

Everything here runs in simulation only (Verilator + Python), with no FPGA attached.
Base design: https://github.com/ilmiahmad/tpuv1 (unmodified RTL).

## 1. tpuv1 simulates cleanly with free tools

| Testbench | Result |
|---|---|
| `tb_matrix_unit` (16x16 systolic array), 5 golden cases | 5/5 pass |
| `tb_tpu_core` (decoder + array + accumulators + activation + AXI fabric), MLP cases | 37/37 pass |
| `tb_tpu_core`, CNN cases (`compile_cnn.py`) | 62/62 pass |
| Python: ISA sim, GEMM ref | pass |

How to get there:
- You need Verilator 5.030 or newer. I used 5.038, built from source. Ubuntu's 5.020 builds the core but miscompiles the PULP `axi_xbar` address map: every AXI write returns DECERR.
- Fetch the PULP `axi` and `common_cells` repos at the `Bender.lock` revisions. No Bender is needed. Pass `-y common_cells/src/deprecated` because `axi` still uses the old `fifo_v3` names.
- The exact command line is in `run_all.sh`.

## 2. The JEPA model (what "hard-coded" means here)

The model is a tiny I-JEPA ViT encoder (`model.py`, `train.py`). It is pre-LN and has no CLS token.

| | |
|---|---|
| Input | 32x32 grey image (MNIST, padded), patch 4, 64 tokens |
| Encoder | dim 128, 6 blocks, 4 heads, MLP 512, GELU |
| Parameters | 1.20 M (INT8, so about 1.2 MB) |
| Training | I-JEPA: EMA target encoder, block-mask predictor, 2 epochs on CPU (7 min) |

Only the encoder goes into RTL. The predictor is used for training only.

Real I-JEPA models (ViT-H, 632 M params) are about 500x too big for the 2.9 MB of on-chip RAM on the KV260. Anything you hard-code on this board will be a model of roughly 1 to 1.5 M params.

Representation quality is weak because the training was very short. A linear probe on mean-pooled features scores 60% after 2 epochs, against 63% at random init, using 2k labels. The point of this run was the hardware flow, not accuracy. Training longer, or on CIFAR (blocked from this sandbox), is the next step for quality.

## 3. Integer graph (bit-exact spec): `intops.py`, `quantize.py`

- **Matmuls:** INT8 x INT8 -> INT32 with per-channel TFLite requant. This is exactly what tpuv1's activation unit already does. It was cross-checked against tpuv1's `tflite_int8.py` on 20k random cases with 0 mismatches.
- **Folded into weights:** the LayerNorm gamma/beta and the attention 1/sqrt(d) scale.
- **New operations, all integer-only:**
  - LayerNorm: one pass that accumulates sum and sum of squares, then `isqrt`, then a reciprocal, then multiply.
  - Softmax: a 256-entry exp LUT, then a sum, then a reciprocal. Output probabilities are 0..127.
  - GELU: a 256-entry int8 -> int8 LUT per layer.
  - Residual add: `sat8((a*Ma + b*Mb + 2^15) >> 16)`.
- **Accuracy vs float PyTorch:** cosine similarity of encoder outputs averages **0.998** (minimum 0.997) over 200 test images.

## 4. RTL results (trained model, test image #7)

**TPU core with hard-coded weights.** `tb/tb_tpu_core_rom.sv` is tpuv1's own core testbench with one change. The Weight FIFO and Instruction FIFO are fed from `rtl/rom_stream.sv` (a BRAM ROM, `$readmemh`) instead of from the host.

- All **73 encoder matmuls** pass **bit-exact** in the UB output. That covers embed, QKV, proj, fc1 and fc2 for 6 layers, plus Q·Kᵀ and P·V for each of 4 heads. The total is 81.9 M MACs.
- Each case is generated by tpuv1's own compiler. It is checked against tpuv1's ISA simulator first, then run in Verilator.

**Vector unit.** `rtl/vpu.sv` with `tb/tb_vpu.sv` replays every non-matmul op of the same inference, with random back-pressure:

- 832 LayerNorm, 1,536 softmax, 384 GELU and 832 residual-add jobs.
- 31,744 output rows, all **bit-exact**.

Each RTL stage matches the integer graph exactly. So the RTL computes the same encoder output as `quantize.int_forward`, which in turn has 0.998 cosine similarity to PyTorch.

**Speed (100 MHz, from the core's perf counters):**

| | Weights from host (AXI) | Weights from ROM |
|---|---|---|
| Matmul busy time | 5.5 ms | **4.1 ms** |
| Weight stalls | 142k cycles | **0** |
| Array utilisation | 58% | **78%** |

The vector unit adds about 1.8 ms if it runs serially. The total is about 6 ms per image, or roughly 170 images/s.

**Memory if everything is hard-coded:** weights 1,154 KiB + position embedding 8 KiB + unrolled program 404 KiB = 12.8 Mb. That is right at the free on-chip RAM: the XCK26 has 23.6 Mb and tpuv1 already uses 10.8 Mb, mostly for its 1 MiB Unified Buffer. This model only needs about 64 KiB of activations.

## 5. (first pass) What tpuv1 still lacked

1. **Weights from UB.** Q·Kᵀ and P·V use activations as the "weights". tpuv1 only loads weights from the Weight FIFO. In simulation I streamed K/V tiles in as weights. On chip this needs a UB-to-weight-loader path, including a transpose for Kᵀ, and a `MATMUL` flag to select it.
2. **Integrate the VPU.** Add a `VECTOR` opcode in `decoder.sv`, with UB read ports (2 rows/cycle for the add) and a write port. The `ACTIVATE.eltwise` field, already reserved, could carry the residual add. GELU can move into `activation_unit` as a LUT `func`; the sigmoid/tanh codes are reserved for this already.
3. **Shrink the program.** It is 404 KiB because every 16-column tile repeats 33 `SET_CONFIG`s. Options are a requant-parameter ROM indexed by layer, or a small loop/sequencer, which would bring it to a few KiB. With that and a UB cut to 128 KiB, the design fits comfortably.
4. **Full-chain test.** Write one program for the whole encoder, run from ROM after reset, and compare the final UB contents with PyTorch. Then synthesise in Vivado for timing and resources. The VPU's 16 lanes of 49-bit multiplies in the LayerNorm emit stage are the likely critical path, so register them.
5. **Better model.** Train longer and/or on a richer dataset. Optionally keep the residual stream in int16 for headroom.

## 6. End-to-end: the whole encoder from ROM, after reset (`jepa_top`)

`rtl/jepa_top.sv` puts a **sequencer** in front of the *unmodified* tpuv1 `tpu_core`. It also holds the VPU and four ROMs: program, weights and data, requant parameters, and LUTs.

After `run`, it executes one program to the end. The host only places the 32x32 image in the UB.

`tb/tb_jepa_top.sv` wraps it with tpuv1's `tpu_fabric`, which provides the UB and ACC memories. It checks the encoder output in the UB against `compile_jepa.Machine`.

**Results:**
- The output is **bit-exact on test images 0, 3 and 7**.
- Cosine similarity to PyTorch float is 0.998, 0.998 and 0.997 for those three images.
- The machine model is tpuv1's own ISA simulator, with its hazard checker on, plus the extension ops.
- It is asserted equal to `quantize.int_forward`.

**Sequencer extension ops.** All have opcode >= 0x40, are decoded before tpuv1 sees them, and are encoded in `compile_jepa.py`.

| op | does |
|---|---|
| `X_WROM n` | stream the next n weight-ROM words into the Weight FIFO (background) |
| `X_WUB tr base stride kt nt` | UB activations -> Weight FIFO as tiles, with transpose: Kᵀ for Q·Kᵀ, V for P·V |
| `X_MM q sync kt in acc out entry B` | one output tile: [SYNC], kt x MATMUL, 33 SET_CONFIGs from the param ROM, SYNC, ACTIVATE |
| `X_VEC op rows a b o count rstride vstride` | run `count` LayerNorm / softmax / GELU / residual-add jobs over UB vectors |
| `X_LUT`, `X_VCFG`, `X_UBROM`, `X_LOADQ` | load a VPU LUT, set add multipliers + softmax numerator, copy ROM -> UB (position embedding), load one requant set |

Ops that touch the UB wait for the core to drain, then own the UB ports. Everything else streams beside the core.

**Optimisation steps (cycles at 100 MHz, every step still bit-exact):**

| step | cycles | time | change |
|---|---|---|---|
| first working version | 812,332 | 8.12 ms | |
| vector unit: streamed UB reads, 2-bit/cycle divider and sqrt, shorter softmax divide | 579,476 | 5.79 ms | VPU 363k -> 130k cycles |
| `X_MM` macro | 579,476 | 5.79 ms | program 111 KiB -> **12 KiB** (7,135 -> 742 instructions) |
| matmuls before config, 4 ACC regions rotating with the 4 requant sets | 510,277 | 5.10 ms | SET_CONFIG and ACTIVATE now overlap the array; core sync stalls 75k -> 26k |
| double-buffered VPU (next vector loads while the last one computes) | **466,352** | **4.66 ms** | VPU 130k -> 87k |

At 4.66 ms the 16x16 array is busy 69% of the time; its floor is 320k cycles (3.2 ms). What remains:
- about 87k cycles where the VPU and the core run one after the other;
- 41k non-array core cycles;
- 14k cycles of `X_WUB`.

Next levers:
- Overlap the VPU with the next matmul, for example softmax of head h with Q·Kᵀ of head h+1.
- Pipeline `X_WUB`.
- A 32x32 array. That is an ISA-level change in tpuv1, because rows are 16 bytes.

**Memory for full hard-coding (from `compile_jepa.py`):**

| contents | size |
|---|---|
| weight/data ROM | 1,162 KiB |
| requant-param ROM | 68 KiB |
| LUT ROM | 6 KiB |
| program | 12 KiB |
| **total** | **1,248 KiB (10.2 Mb)** |

The UB working set is only 125 KiB, against tpuv1's 1 MiB UB.

Important hardware catch: **UltraRAM cannot be initialised from the bitstream; only BRAM can.** The XCK26 has 144 BRAM36, about 5 Mb, and tpuv1 already uses 44 of them. So the 10 Mb of weights for this 1.2 M-param model cannot all be bitstream ROM. There are two ways to really hard-code it:
- **(a) Load at boot.** Keep the weights in URAM and fill them once at boot, from QSPI flash or the boot image, using a small loader. There is still no per-inference host involvement.
- **(b) Shrink the model** to about 300k params, for example dim 96 and 3 blocks, so it fits in the remaining ~100 BRAM36.

Either way, shrink the UB to 128 KiB. That needs `UbRows` changed in tpuv1's `tpu_pkg`, and frees about 25 URAM.

Correction to the first version of this README: the "AXI writes land one row off" problem was a race in my testbench, not in the PULP xbar. The testbench drove signals exactly on a clock edge. With that fixed, `tb_jepa_top` writes the image and reads the result over AXI again.

## 7. Weights in UltraRAM, loaded once at boot (+ per-layer softmax scale)

**Boot load.** The weight/data memory in `jepa_top` is now a RAM with `ram_style = "ultra"`. It has a boot load port: `wload_valid/ready/data/last`, plus `weights_ready`. `run` is held off until the last word has arrived.
- `tb_jepa_top` streams the 74,368-word image (`wrom.hex`) through the port with 10% random source gaps. That takes 82,633 cycles, **0.83 ms**.
- It then writes the image over AXI and runs the encoder.
- The result is bit-exact on test images 0, 3 and 7.
- The program, requant parameters and LUTs are only 86 KiB. They stay as BRAM, so they are true bitstream ROM.

**On the board** (not built yet):
1. The weight image ships as a file in the boot image or the root filesystem.
2. At boot, the PS copies it into a DDR buffer.
3. tpuv1's iDMA streams it through HP0 into the load port, about 1.2 MB in under 1 ms.

The cleanest hook is an AXI write window for the load port in `tpu_fabric`, next to the WFIFO window, so iDMA (or the CPU) can write it like any other slave. This happens once per power-up. There is no host work per inference.

**Fit on the XCK26 (estimate):**

| memory | contents | blocks |
|---|---|---|
| UltraRAM, 64 available | weights: 74,368 x 128 bit = 2 URAM wide x 19 deep | 38 URAM |
| UltraRAM | UB cut to 8,192 rows (the program uses 8,000) | 4 URAM |
| UltraRAM | **total** | **42 of 64** |
| BRAM36, 144 available | program ~4 + params ~16 + LUTs ~2 | ~22 |
| BRAM36 | tpuv1's existing use | 44 |
| BRAM36 | **total** | **~66 of 144** |

Shrinking the UB is **required**: tpuv1's 1 MiB UB alone takes 32 URAM. That is a one-line `UbRows` change in tpuv1's `tpu_pkg`, which I have not made here.

**Per-layer softmax numerator.** Softmax now outputs `min(round(p*q), 127)` at scale 1/q, with q chosen per layer by MSE on the calibration set. This follows the finding in tpu-stack's `quant/results/jepa_report.md`.
- The chosen q values for the 6 layers are 599, 263, 263, 247, 287 and 167, instead of a fixed 127.
- q travels in `X_VCFG.sq` (bits [63:50]) and reaches the VPU through `cmd_ma` for softmax jobs.
- The divider runs 10 cycles instead of 7.
- Cosine similarity to PyTorch rises from 0.9981 to **0.9991** (200 test images). On images 0, 3 and 7 it is 0.9992, 0.9991 and 0.9992.
- The encoder now takes 470,960 cycles, **4.71 ms**.
