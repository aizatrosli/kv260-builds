# TPU-KV260 simulation + a hard-coded tiny JEPA encoder

Everything here runs in simulation only (Verilator + Python), with no FPGA attached.
Base design: https://github.com/ilmiahmad/tpuv1 (unmodified RTL).

## 1. tpuv1 simulates cleanly with free tools

| Testbench | Result |
|---|---|
| `tb_matrix_unit` (16x16 systolic array), 5 golden cases | 5/5 pass |
| `tb_tpu_core` (decoder + array + accumulators + activation + AXI fabric), MLP cases | 37/37 pass |
| `tb_tpu_core`, CNN cases (`compile_cnn.py`) | 62/62 pass |
| Python: ISA sim, GEMM ref | pass |

How to get there:
- You need Verilator 5.030 or newer. I used 5.038, built from source. Ubuntu's 5.020 builds the core but miscompiles the PULP `axi_xbar` address map: every AXI write returns DECERR.
- Fetch the PULP `axi` and `common_cells` repos at the `Bender.lock` revisions. No Bender is needed. Pass `-y common_cells/src/deprecated` because `axi` still uses the old `fifo_v3` names.
- The exact command line is in `run_all.sh`.

## 2. The JEPA model (what "hard-coded" means here)

The model is a tiny I-JEPA ViT encoder (`model.py`, `train.py`). It is pre-LN and has no CLS token.

| | |
|---|---|
| Input | 32x32 grey image (MNIST, padded), patch 4, 64 tokens |
| Encoder | dim 128, 6 blocks, 4 heads, MLP 512, GELU |
| Parameters | 1.20 M (INT8, so about 1.2 MB) |
| Training | I-JEPA: EMA target encoder, block-mask predictor, 2 epochs on CPU (7 min) |

Only the encoder goes into RTL. The predictor is used for training only.

Real I-JEPA models (ViT-H, 632 M params) are about 500x too big for the 2.9 MB of on-chip RAM on the KV260. Anything you hard-code on this board will be a model of roughly 1 to 1.5 M params.

Representation quality is weak because the training was very short. A linear probe on mean-pooled features scores 60% after 2 epochs, against 63% at random init, using 2k labels. The point of this run was the hardware flow, not accuracy. Training longer, or on CIFAR (blocked from this sandbox), is the next step for quality.

## 3. Integer graph (bit-exact spec): `intops.py`, `quantize.py`

- **Matmuls:** INT8 x INT8 -> INT32 with per-channel TFLite requant. This is exactly what tpuv1's activation unit already does. It was cross-checked against tpuv1's `tflite_int8.py` on 20k random cases with 0 mismatches.
- **Folded into weights:** the LayerNorm gamma/beta and the attention 1/sqrt(d) scale.
- **New operations, all integer-only:**
  - LayerNorm: one pass that accumulates sum and sum of squares, then `isqrt`, then a reciprocal, then multiply.
  - Softmax: a 256-entry exp LUT, then a sum, then a reciprocal. Output probabilities are 0..127.
  - GELU: a 256-entry int8 -> int8 LUT per layer.
  - Residual add: `sat8((a*Ma + b*Mb + 2^15) >> 16)`.
- **Accuracy vs float PyTorch:** cosine similarity of encoder outputs averages **0.998** (minimum 0.997) over 200 test images.

## 4. RTL results (trained model, test image #7)

**TPU core with hard-coded weights.** `tb/tb_tpu_core_rom.sv` is tpuv1's own core testbench with one change. The Weight FIFO and Instruction FIFO are fed from `rtl/rom_stream.sv` (a BRAM ROM, `$readmemh`) instead of from the host.

- All **73 encoder matmuls** pass **bit-exact** in the UB output. That covers embed, QKV, proj, fc1 and fc2 for 6 layers, plus Q·Kᵀ and P·V for each of 4 heads. The total is 81.9 M MACs.
- Each case is generated by tpuv1's own compiler. It is checked against tpuv1's ISA simulator first, then run in Verilator.

**Vector unit.** `rtl/vpu.sv` with `tb/tb_vpu.sv` replays every non-matmul op of the same inference, with random back-pressure:

- 832 LayerNorm, 1,536 softmax, 384 GELU and 832 residual-add jobs.
- 31,744 output rows, all **bit-exact**.

Each RTL stage matches the integer graph exactly. So the RTL computes the same encoder output as `quantize.int_forward`, which in turn has 0.998 cosine similarity to PyTorch.

**Speed (100 MHz, from the core's perf counters):**

| | Weights from host (AXI) | Weights from ROM |
|---|---|---|
| Matmul busy time | 5.5 ms | **4.1 ms** |
| Weight stalls | 142k cycles | **0** |
| Array utilisation | 58% | **78%** |

The vector unit adds about 1.8 ms if it runs serially. The total is about 6 ms per image, or roughly 170 images/s.

**Memory if everything is hard-coded:** weights 1,154 KiB + position embedding 8 KiB + unrolled program 404 KiB = 12.8 Mb. That is right at the free on-chip RAM: the XCK26 has 23.6 Mb and tpuv1 already uses 10.8 Mb, mostly for its 1 MiB Unified Buffer. This model only needs about 64 KiB of activations.

## 5. What tpuv1 still lacks, and the plan

1. **Weights from UB.** Q·Kᵀ and P·V use activations as the "weights". tpuv1 only loads weights from the Weight FIFO. In simulation I streamed K/V tiles in as weights. On chip this needs a UB-to-weight-loader path, including a transpose for Kᵀ, and a `MATMUL` flag to select it.
2. **Integrate the VPU.** Add a `VECTOR` opcode in `decoder.sv`, with UB read ports (2 rows/cycle for the add) and a write port. The `ACTIVATE.eltwise` field, already reserved, could carry the residual add. GELU can move into `activation_unit` as a LUT `func`; the sigmoid/tanh codes are reserved for this already.
3. **Shrink the program.** It is 404 KiB because every 16-column tile repeats 33 `SET_CONFIG`s. Options are a requant-parameter ROM indexed by layer, or a small loop/sequencer, which would bring it to a few KiB. With that and a UB cut to 128 KiB, the design fits comfortably.
4. **Full-chain test.** Write one program for the whole encoder, run from ROM after reset, and compare the final UB contents with PyTorch. Then synthesise in Vivado for timing and resources. The VPU's 16 lanes of 49-bit multiplies in the LayerNorm emit stage are the likely critical path, so register them.
5. **Better model.** Train longer and/or on a richer dataset. Optionally keep the residual stream in int16 for headroom.
