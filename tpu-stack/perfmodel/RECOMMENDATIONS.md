# KV260 TPU: hardware recommendations (from `tpuperf`)

Generated by `python -m tpuperf report`. Every number below comes from the cycle-approximate model in `tpuperf/`, calibrated against the tpuv1 board measurements and the jepa-tpu Verilator runs (table at the end). Treat speedups as +-15 %.

## Bottom line

* tpuv1 as built runs the jepa encoder in **6.29 ms** (matmul 4.65 ms + serial VPU 1.63 ms, 159 img/s).
* The recommended KV260 design (32x32 array, 200 MHz, DSP packing, double-buffered weights, weights in URAM, streamlined control, pipelined/overlapped VPU) runs it in **0.582 ms** (**10.8x**, 1717 img/s) using ~83k LUT, 744 DSP, 82 BRAM36, 48 URAM (tight).
* 64x64 and 32x64/64x32 arrays do not fit the XCK26 (DSP and LUT), even with packing. 32x32 needs DSP packing to leave DSPs for the requant lanes and the VPU.
* The as-built design is control-bound, not MAC-bound: per output-column tile it spends 2C+1 SET_CONFIGs (2 cycles each) that wait for the previous ACTIVATE to drain, plus a full SYNC(MATRIX) drain. That costs more than weight bandwidth does at batch >= 64 rows.

### What each one is

1. **32x32 array with DSP packing (2 INT8 MAC / DSP48E2)** (effort 4). 4x MACs for ~2x DSPs; UB/ACC/WFIFO widths double. Needs packing correction logic.
2. **200 MHz clock** (effort 4). Pipeline DSPs (A/B/M/P regs), register the requant/VPU multipliers, retime decoder legality checks. DDR latency in cycles doubles.
3. **Streamlined control (requant-param table, no per-tile SYNC, ACT overlaps)** (effort 2). Per-layer requant table indexed by column tile (1 instr instead of 2C+1 SET_CONFIG), SET_CONFIG no longer waits for ACTIVATE, ACC ping-pong without SYNC(MATRIX) per tile, GELU as an activation-unit LUT. Decoder/act_seq + compiler change, ~0 resources.
4. **VPU integrated, pipelined and overlapped with the array** (effort 3). VECTOR opcode with its own UB ports so LayerNorm/softmax/residual run while the array computes the next GEMM; isqrt/divide of one job overlap the next job's rows.
5. **Double-buffered weight shadow** (effort 2). Second shadow register bank per PE, loaded alternately: the next tile loads while the previous one waits for its swap. Min tile period (2R+C+1)/2 instead of 2R+C+1 (49 vs 97 cycles at 32x32), i.e. 64-token tiles stop stalling.
6. **Weights resident on chip (URAM ROM)** (effort 1). Only for models <= ~1.5 MB INT8: preload weights into URAM once (UB cut to 256 KiB).
7. **Decoupled weight prefetch DMA (large bursts into the Weight FIFO)** (effort 2). A weight-stream engine that runs ahead of MATMUL bounded by FIFO space, one DMA per layer instead of one 256 B READ_WEIGHTS per tile. Hides DDR latency.
8. **UB -> weight-loader path for Q.K^T / P.V** (effort 2). Read K/V tiles from the UB into the weight shift chain (with transpose for K^T) instead of a DDR round trip. One mux + address generator.

### Suggested implementation order for the KV260

The score ranks raw value per effort; the order below also respects dependencies (cheap enablers first, then the array that needs them).

1. **Streamlined control** (effort 2): 1.16x alone, 1.29x lost if left out of the final design. Compiler + decoder/act_seq only, no resources, no timing risk. Its share grows as the array gets wider (2C+1 SET_CONFIGs per column tile).
2. **Double-buffered weight shadow** (+1024 LUT at 16x16): 1.00x on tpuv1 today (64-row tiles already cover the 49-cycle period) but 1.17x lost without it in the 32x32 design, where the single-shadow period is 2R+C+1 = 97 cycles > 64 tokens.
3. **32x32 array with DSP packing**: 2.44x alone, 3.47x lost without it; +37280 LUT, +368 DSP, +39 BRAM36. The full recommended design lands at 83k LUT (71 %), 744 DSP (60 %), 82 BRAM36, 48 URAM with jepa weights resident.
4. **200 MHz** (effort 4): 1.97x on everything; hardest item (tpuv1 has +1.25 ns slack at 100 MHz, i.e. ~114 MHz). 150 MHz is a reasonable intermediate target (see the array x clock table).
5. **Integrated, pipelined, overlapped VPU**: 1.39x lost without it. Once the array is ~8x faster the serial VPU (LayerNorm isqrt + divide, softmax divide: 52 / 30 scalar cycles per job) dominates transformer time; beyond overlap, a parallel divider per lane group is the next step.
6. **Weights on chip / weight prefetch / UB->weight path**: each is worth only 1.03x / 1.03x / 1.01x in time. With 64-row tiles one 256 B READ_WEIGHTS per tile already hides behind compute; the 58 % util of the jepa 'AXI' Verilator run came from the testbench's ~2.35 B/cycle push rate, not from DDR (an HP port sustains ~12.8 B/cycle). Keep weights on chip for jepa-sized models because it removes DDR traffic and makes latency deterministic, not for speed.

## Caveats

* Board measurements are wall time of one job; the model's fixed host overhead is a fit.
* VPU numbers assume the jepa-tpu vpu.sv FSM widened to C lanes; GELU fused into the activation LUT in the recommended design.
* Resource coefficients are linear fits around one measured build (16x16). Expect +-20 % at 32x32; the DSP count is exact arithmetic, the LUT count is not.
* No DDR contention from the PS, no refresh, no TLB/IOMMU effects.
* CNN stems use host-side im2col; depthwise convs map one channel per column (1/R useful lanes), which is why MobileNetV2 utilisation is low.
